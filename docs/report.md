# Краткий отчёт: рекламная аналитика на ClickHouse

## Цель и данные

Задача - хранить рекламные события и рассчитывать дневные KPI по кампаниям и каналам. Подготовлены справочники `channels`, `campaigns`, исходная таблица `raw_ads_events` и витрина `campaign_kpi`.

Для проверки создано 36 000 событий за 1–20 ноября 2026 года (6 кампаний × 20 дней × 300 событий). Использованы три типа событий (`impression`, `click`, `conversion`), три устройства и четыре страны. Данные синтетические: отдельных пользователей и переходов между этапами воронки нет.

## Архитектура и выбор хранения

Для всех четырёх таблиц выбран `MergeTree`: в проекте нужны обычные вставки, группировки и чтение диапазонов данных, без специальных сценариев версионирования или удаления дублей движком. Справочники небольшие, поэтому в них достаточно `ORDER BY` по идентификатору и не требуется партиционирование.

`raw_ads_events` сортируется по `(campaign_id, event_date, channel_id, event_id)`: удобен просмотр событий конкретной кампании за период. Для `campaign_kpi` использован `(event_date, campaign_id, channel_id)`, поскольку отчёты часто ограничиваются датами. Обе таблицы партиционируются по `toYYYYMM(event_date)`: это разумный уровень для помесячного хранения истории, без множества мелких ежедневных партиций.

Для `event_type`, `device` и `country` применён `LowCardinality(String)` из-за малого числа уникальных значений. Денежные поля - `Decimal`. TTL составляет 1 год для сырых событий и 2 года для итоговой витрины. Храним агрегаты дольше, так как они компактнее и полезны для сравнения периодов. Удаление по TTL происходит фоново.

## ETL и метрики

Заполнение витрины выполняется через `INSERT ... SELECT`: группировка по `(campaign_id, event_date, channel_id)`, `countIf` для типов событий, `sum` для расходов и доходов. В модели расходы возникают на клике, доход - на конверсии.

Формулы: `CTR = clicks / impressions × 100`, `CVR = conversions / clicks × 100`, `CPA = spend / conversions`, `ROI = (revenue − spend) / spend × 100`. При отсутствии знаменателя записывается 0. Это техническое соглашение учебной модели, а не утверждение о нулевой стоимости привлечения. При анализе за несколько дней показатели вычисляются из агрегированных сумм, а не усреднением дневных процентов.

Витрина пересобирается целиком. `Materialized View` не использовано: данных немного, а полная пересборка проще для проверки и повторного запуска. Для потока новых событий потребовалась бы инкрементальная схема и учёт повторных/запаздывающих событий.

## Проверка результата

| Показатель | Результат |
| --- | ---: |
| Каналы / кампании | 4 / 6 |
| Сырые события / строки витрины | 36 000 / 120 |
| Показы / клики / конверсии | 35 019 / 871 / 110 |
| Расходы / доходы | 389 526 ₽ / 356 113 ₽ |
| Совпадение исходных событий и агрегатов | Да |
| Дубликаты ключа дневной витрины | Не обнаружены |

Пять отчётов возвращают осмысленные результаты. За весь период у кампании 101 максимальный ROI - 42,87% при CTR 0,52%. В последние семь дней представленных данных лучший ROI у кампании 103 - 44,14%. Минимальный CPA среди каналов у VK Ads - 3 321,27 ₽. Кампания 104 20 ноября превысила дневной бюджет на 2 370 ₽ (47,4%). Высокая кликабельность не гарантирует высокий ROI - это видно при сравнении кампаний.

По `system.parts` все таблицы содержали по одной активной части; сырые события занимали примерно 630 KiB, витрина - 11 KiB. На момент проверки `system.merges` был пуст. В `system.query_log` пять отчётов выполнялись за 3–10 мс в первом замере и за 2–36 мс при повторном запуске. Выводы о скорости при больших объёмах по этим результатам делать нельзя: сама витрина содержит всего 120 строк.

Выполнено восстановление проекта с нуля в отдельном Docker-контейнере: все шесть SQL-файлов выполнились без ошибок, количества и суммы совпали с основной базой. Проверки выполнены вручную через SQL; отдельная автопроверка учебной платформы не запускалась.
